# Blog Post Style Guide

写博客文章时严格遵循以下规范。

## 定位

我们的读者可能是技术小白，也可能是资深工程师。文章要做到：**小白能读懂，老手能看到深度**。这两个目标不矛盾——关键是把逻辑链讲清楚，而不是堆术语或降智。

## 文件结构

每篇文章一个目录 `src/content/blog/<slug>/`，内容文件固定为 `index.md`，图片与 `index.md` 同目录，用相对路径 `./image.png` 引用。Excalidraw 源文件（`.excalidraw`）也可以放同目录，方便后续修改。

## Frontmatter

```yaml
---
title: "中文标题"
description: "一段话描述文章内容，不超过 100 字"
pubDate: "YYYY-MM-DD"
tags: ["Tag1", "Tag2", "Tag3", "Tag4"]
hexagram: "䷂"    # 可选，易经卦象
element: "metal"   # 可选，water/wood/fire/metal
---
```

## 文章结构

1. **TL;DR**：紧跟 frontmatter，`**TL;DR:**` 开头，1-3 句话概括全文核心论点。让读者快速决定要不要继续读。
2. **前置知识**：blockquote 格式，包含站内交叉链接。
3. **`---` 分隔符**
4. **正文 H2 章节**：每个大章节之间用 `---` 分隔。
5. **局限性与权衡**：倒数第二个章节，诚实讨论技术的边界和不适合的场景。
6. **进一步阅读**：最后一个章节，格式为 `- [标题](URL) — 一句话描述`。

## 写作风格

### 核心原则：问题驱动的叙事

每个章节的叙事逻辑是：

**出现了什么问题 → 为什么会有这个问题 → 什么技术/方案解决了它 → 这个方案怎么工作（机制、代码、公式） → 具体数字/例子 → 有什么代价/局限 → 引出下一个问题**

这样读者跟着你的思路走，而不是被塞一堆概念。参考 DEX 交易机制那篇文章的结构——每个小节都在解决上一个小节留下的问题。

**不要这样写**：

> Skills 是按需加载的独立指令文件。与系统提示不同，Skills 不是每次会话都注入的——只有当任务需要时才加载。

这是在罗列特性，读者不知道为什么要关心。

**要这样写**：

> CLAUDE.md 解决了通用规则的注入问题，但它有一个限制：上下文窗口是有限的。一个中等项目可能涉及数据库迁移规范、API 设计约定、前端组件规范等十几个知识领域。全塞进 CLAUDE.md，留给实际工作的空间就不够了。
>
> Skills 就是为了解决这个问题。它是按需加载的独立指令文件——只在任务需要时才注入上下文。

先讲清楚问题（上下文不够用），再讲方案（按需加载），读者自然理解为什么要这么做。

### 可读性

- 中文为主，关键技术术语保留英文
- 适当铺垫和过渡，但不要废话段落
- 一个段落讲清楚一个意思，不要一句话一个意思地碎碎念
- 能用类比帮助理解的地方用类比，但类比要准确
- 代码示例要完整、可直接使用，附带关键注释

### 技术深度

- 涉及机制时给出具体的数字、公式或代码，不要停留在概念描述
- 讲「为什么这样设计」而不只是「是什么」
- 讨论权衡和边界条件，不要只讲好处
- 用具体场景举例（比如「一个 50 个文件的代码库」而不是「大型项目」）

### 跨站引用

- 用相对路径：`[Spec 驱动开发](/blog/spec-driven-development)`
- 在「前置知识」和正文中自然引用相关文章

## 画图

核心难懂的概念、架构关系、流程用 Excalidraw 画图。文字讲不清楚的，一张图就够了。

### 图片规范

- 格式：SVG（数学/技术图）或 PNG（流程/架构图）
- 与 `index.md` 同目录存放
- 引用方式：`![图的描述](./filename.png)`
- 可交互版本：包裹在链接里 `[![图的描述](./image.png)](https://excalidraw.com/#json=...)`

### 视觉风格

参考 `skills/excalidraw-style.md`，核心要点：
- 配色：玉石绿 `#4A8B71`（正确路径/核心组件）、朱砂红 `#D13429`（风险/异常）、深灰 `#474747`（文字/线条）
- 形状：直角矩形代表实体/模块，平滑箭头代表数据流，菱形代表决策点
- 字体：等宽字体（Monospace）
- 去掉不必要的装饰，保持高信噪比

### 什么时候画图

- 架构关系（组件之间怎么配合）→ 架构图
- 多步骤流程（数据怎么流转）→ 流程图
- 概念对比（方案 A vs 方案 B 的区别）→ 对比图
- 数学/算法（曲线形态、数据结构）→ 技术示意图

## 写作流程

用户通常提供碎片化的技术内容（聊天记录、技术笔记、零散的想法）。AI 的工作是：

1. **理解核心论点**：这篇文章到底要传达什么？
2. **梳理逻辑链**：按照「问题驱动」的方式重新组织内容
3. **补充技术深度**：加入具体的机制解释、数字、代码
4. **画图**：为核心概念创建 Excalidraw 图表
5. **统一语言风格**：按照本规范调整措辞和结构
6. **审查**：用下方清单检查

## 审查清单

- [ ] TL;DR 能不能让读者 10 秒内决定要不要读？
- [ ] 每个章节是不是先讲问题再讲方案？
- [ ] 有没有具体的数字或代码示例？
- [ ] 难懂的地方有没有画图？
- [ ] 「局限性与权衡」是否诚实具体？
- [ ] 「进一步阅读」链接有效且有描述？
- [ ] 小白能不能读懂核心逻辑？老手能不能看到深度？
